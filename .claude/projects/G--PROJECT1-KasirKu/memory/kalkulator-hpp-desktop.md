Final direction for roadmap item #1 ([[product-roadmap-2026-07]], see [[kalkulator-hpp-standalone]] for the superseded AI-web-tool attempt from earlier the same day). User's explicit goal: sell once, **zero ongoing burden/cost afterward** — no AI, no per-user server cost, no subscription.

**Architecture — two independent halves**:
1. **`desktop-app/`** (new top-level dir, separate `package.json`, NOT part of the Next.js build) — vanilla HTML/CSS/JS Electron app (`main.js`/`preload.js`/`renderer.js`/`index.html`/`style.css`), deliberately no React/Vite to keep the build simple. Data (bahan baku/menu/resep) persisted via `electron-store` (JSON file in OS user-data dir) — **zero network calls once installed**, matches the "no burden" goal literally. HPP/margin math copied from `src/app/kalkulator-hpp/hpp-calculator.tsx` (`hpp/(1-margin)`, already-proven formula).
2. **Selling infrastructure on the KasirKu web app** — extends the existing Midtrans billing system ([[billing-midtrans]]) rather than building new payment infra: new table `public.hpp_desktop_orders` (migration `20260713130000_hpp_desktop_orders.sql`) scoped by **email, not business_id** (guest checkout, buyer has no KasirKu account) — RLS has **zero policies** (service-role only, via `src/lib/supabase/service.ts`, whose comment was updated to document this as a legitimate third use case alongside the webhook/cron). Anonymous status checks go through a new security-definer RPC `get_hpp_order_status(order_id)` (only reveals `download_token` once `status='settlement'`). Order IDs use prefix `HPP-` (vs the existing business-subscription `KK-` prefix) so the **single shared Midtrans webhook** (`src/app/api/midtrans/notification/route.ts`) can branch — extended, not duplicated, the existing `KK-` path is untouched. New pages: `/kalkulator-hpp/beli` (product + email + buy button, respects the existing `BILLING_MANUAL_MODE` toggle exactly like the business billing page) and `/kalkulator-hpp/beli/selesai` (polls `get_hpp_order_status` every 3s, up to ~2 min, then shows the download link). Download itself is gated by a new route `src/app/api/kalkulator-hpp-desktop/download/route.ts` which verifies `order+token` against the DB before streaming the installer from `private-assets/` (deliberately outside `public/`, gitignored, so the URL can't be guessed/shared without a valid paid token).

**Pricing**: placeholder Rp49.000 in `src/lib/billing/desktop-products.ts` — user hasn't given a real price, same "edit before going live" caveat as the main `plans.ts` prices.

**Known gap, accepted for v1**: no email-sending integration exists in this codebase at all — the download link only ever appears on the `/beli/selesai` page after payment; if a buyer closes that tab before downloading, they must contact support manually today. Flagged as a fast-follow (e.g. Resend) if it becomes a real problem.

**UI redesign, same day 2026-07-13**: user rejected the original flat two-card layout ("saya ga mau tampilan seperti itu") and requested a full redesign — approved via an interactive HTML mockup shown through `mcp__visualize__show_widget` *before* touching real code (user's explicit standing instruction for this feature: preview first, "jangan langsung jadi tiba-tiba tanpa saya iyakan"). Iterated through 3 mockup rounds (color/icons/layout feedback, then added features) before getting final go-ahead ("oke manteb... lanjut kerjakan"). Implemented in `desktop-app/`:
- **Layout**: left sidebar nav (Dashboard / Bahan Baku / Menu) replacing the old stacked-cards page; colors now match KasirKu's actual brand green (`--color-brand-500 #00a651` family from `src/app/globals.css`), not the generic blue used in the first mockup draft — user explicitly rejected black sidebars and emoji-style icons (all nav/action icons are inline line-style SVGs now).
- **Dashboard**: stat cards (Total Menu, Total Bahan Baku, Rata-rata Margin, Rata-rata HPP + its %-of-selling-price sub-line) plus two charts — a wide horizontal-bar "Rata-rata HPP per Kategori" (grouped by menu category) and a deliberately small/narrow vertical-bar "Margin per Menu" (user asked to shrink this one — "kecilkan bar bagian kanan").
- **Bahan Baku**: added Excel/CSV import (`xlsx` npm package, parsed in the **main process** via a new `dialog:importExcel` IPC handler — renderer has no filesystem access since `nodeIntegration: false`; column matching is fuzzy on header names containing "nama/name/bahan", "satuan/unit", "harga/cost/price"). Import upserts by case-insensitive name match (updates price if the ingredient already exists, else adds new).
- **Menu**: `menuItems` gained `category` (free text) and `sellingPrice` fields (previously only had `targetMarginPercent`); table now shows Menu/Kategori/Total HPP/Harga Jual/%HPP/Margin with click-to-expand detail rows (edit category+price, manage recipe lines) — same interaction pattern as the old ingredient/menu cards, just reshaped into table rows.
- **Menu Bundling (new entity)**: `state.bundles` — a bundle references existing `menuItems` by id+qty; its HPP is simply the sum of each component menu's own `computeHpp()` × qty (no separate ingredient list). Has its own sellingPrice/%HPP/margin computed the same way as single menus. Lives in a second subtab within the Menu panel ("Menu Satuan" / "Menu Bundling").
- **Sidebar category nav**: clicking "Menu" in the sidebar expands a sub-list of categories (derived dynamically from `menuItems`, deduped, "Tanpa Kategori" fallback for blank categories) — clicking one filters the Menu Satuan table and shows a breadcrumb.
- **Download HPP Menu**: button in Menu Satuan exports the current table (Menu/Kategori/Total HPP/Harga Jual/%HPP/Margin) to `.xlsx` via a new `dialog:exportMenuHpp` IPC handler (main process writes the file after a native save dialog) — confirmed with user as Excel format, not CSV.
- **Backup / Pulihkan Data**: two buttons in the sidebar footer. Backup writes the entire `electron-store` contents (`ingredients`/`menuItems`/`bundles`) to a single `.json` file the user picks via native save dialog (`dialog:backupData`); Restore reads a `.json` file back (`dialog:restoreData`, validates the three arrays exist), asks for confirmation (it overwrites current data), then persists. Confirmed with user as JSON format, not Excel — "paling aman untuk dipulihkan persis sama seperti semula".
- All three new IPC handlers (`dialog:importExcel`, `dialog:exportMenuHpp`, `dialog:backupData`, `dialog:restoreData`) live in `main.js` alongside the existing `data:get`/`data:set`, and are bridged through `preload.js` the same `contextBridge` way as before — no change to the `contextIsolation: true` / `nodeIntegration: false` security posture.
