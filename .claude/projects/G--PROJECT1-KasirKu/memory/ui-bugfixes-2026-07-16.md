Three issues reported together in one message; two fixed, one still open.

**1. Kembalian (change due) low contrast — FIXED** (`af06d94`): the change-due amount shared the same muted `text-zinc-500`/`text-zinc-600` as its label everywhere it's shown (POS payment panel in both `pos-screen.tsx` and `ticket-pos-screen.tsx`, plus the transaction/ticket detail pages) — bolded + darkened the value (`font-bold text-zinc-900`) in all 4 spots, left the label muted. Not verified live in browser (needs either a real cashier PIN session or seeded transaction data with `change > 0`, neither readily available in the fresh Dev Supabase project — see [[supabase-dev-prod-split]]) — only `tsc`/`eslint` clean. If this ever needs re-checking, that's the gap.

**2. Form text nearly invisible in dark mode — FIXED** (`bd39dc6`): root cause was `src/app/globals.css`'s leftover default-Next.js-template `@media (prefers-color-scheme: dark)` block, which flipped `body`'s `color` to `#ededed` (near-white) whenever a visitor's OS was in dark mode. Every component in this app uses explicit light-mode Tailwind classes (`bg-white`, `text-zinc-900`, etc.) — nothing else in the codebase actually reads `--background`/`--foreground` (confirmed via grep, zero other matches) — so this was a genuinely half-implemented, unused dark-mode remnant. Any element that doesn't set its own explicit text color (the login/signup email/password inputs, specifically) inherited that near-white body color and rendered on a white input background — nearly invisible, exactly matching the report ("kadang ga keliatan sama sekali"). Removed the dark-mode block entirely rather than patch around it, since there's no real dark-mode design to preserve. Verified in browser: forced dark `prefers-color-scheme` via `resize_window`'s `colorScheme` param, confirmed `getComputedStyle` on the email input showed `color: rgb(23,23,23)` (dark, readable) instead of the old near-white — fix holds regardless of visitor OS theme.

**3. General "lemot"/slow feeling on the live site — PARTIALLY ADDRESSED** (`414cf01`): user confirmed this is specifically about slow **initial page load** (not post-load interaction lag) on the deployed production site. Measured via `curl -w`: homepage TTFB ~0.65s warm, ~1.6s cold before the fix — not catastrophic but not fast.

**Root cause found and fixed for the homepage specifically**: `src/lib/supabase/middleware.ts`'s `updateSession()` already calls `supabase.auth.getUser()` on every request (necessary — refreshes the session per Supabase's documented Next.js pattern), and `src/app/page.tsx`'s `Home` Server Component was **independently calling `getUser()` again** — a second Auth-API round-trip on the critical path of every single homepage load, purely to decide whether to redirect an already-logged-in visitor to `/dashboard`. Swapped to `getSession()` (reads the already-refreshed cookie locally, no network call) since this specific check is a UX nicety, not a real access-control boundary.

**Deliberately left alone** (audited via `grep supabase.auth.getUser` — 7 total call sites): `middleware.ts` itself (must stay `getUser()`, that's the one that actually refreshes the cookie), `business/[businessId]/(dashboard)/layout.tsx` (real subscription/access gate), `dashboard/page.tsx` and `admin/page.tsx` (list/show real per-user data), `onboarding/actions.ts` and `billing/actions.ts` (mutations tied to a specific authenticated user, e.g. payments) — all of these need the server-validated `getUser()`, swapping them to `getSession()` would weaken real security checks, not just an optimization.

**Full-app E2E sweep 2026-07-17** (user asked "cek keseluruhan dari fitur-fitur"): committed the previously-stuck receipt auto-print fix (`386ed41` — classifier outage had blocked the commit the day before), then ran statics (41/41 vitest, tsc, eslint all clean) and a full browser walkthrough on the fresh Dev DB: new admin-API-created user (`claude.test.dev@example.com` / `test-kasirku-dev-123`, business "Toko Test Dev" id `b93a088f-15c3-4147-b29a-1342235ab855`, activated to `lifetime` via service-role) → onboarding → billing gate → product+cashier creation → POS PIN → shift open → cash checkout with change → receipt (auto-print confirmed: the print dialog opening is what blocks the Browser-pane renderer — that hang is the success signal, recover by navigating away) → journal auto-posting → every accounting/SDM/ops page (all 200) → all public pages (all 200). **New bug found and fixed during the sweep** (`d662a6c`): "today" was computed as the **UTC** date (`new Date().toISOString().slice(0,10)`) in 13 files — between 00:00–07:00 WIB this points at *yesterday*. Symptom that exposed it: Neraca defaulted to showing all zeros minutes after a sale posted at 00:04 WIB. Affected: Neraca + Rekonsiliasi default as-of dates, form date prefills (jurnal manual, kas harian, invoice baru, expense, receivable, purchase), member validity checks (3 member pages), ticket-report active-member count, Excel export Neraca cutoff. Fixed via new shared `src/lib/wib.ts` → `todayWibDateString()` (the `en-CA`+`Asia/Jakarta` pattern the already-correct pages used). **Rule for future code on this project: never `toISOString().slice(0,10)` for "today" — always `todayWibDateString()`.**

**Not yet done / open**: this only speeds up the homepage's own redundant check — it does NOT address whatever the dashboard, POS, or other pages' first-load latency looks like (each has its own render path and hasn't been profiled). Also unexplored: Vercel cold-start latency, Supabase query latency inside the dashboard/business pages (some report pages do multiple sequential queries), and client-side bundle size. **How to apply**: if "lemot" persists after this homepage fix, next ask specifically *which* page(s) still feel slow to open (dashboard? POS? a report page?) and profile that page's own request waterfall rather than assuming the same getUser()-duplication pattern is the cause everywhere — it was confirmed only for the homepage.

**Round 2, 2026-07-19 — accounting pages specifically, DONE** (user reported "input transaksi jurnal" and other menus feel slow). Investigation agent found: jurnal/neraca/laba-rugi/arus-kas/dashboard-home each ran 3-4 independent Supabase queries sequentially (`await` one after another) instead of `Promise.all`; worse, `arus-kas`'s opening-cash-balance calculation ran a **second full unbounded history scan of every account's journal lines** (no lower date bound, by design — but not filtered to just the Kas account either) on every page load. Fixed:
- `jurnal`, `neraca`, `laba-rugi` page.tsx: business/accounts/entries(/reversals) queries parallelized via `Promise.all` (were sequential).
- `arus-kas/page.tsx`: business+accounts parallelized; the opening-balance query now uses `journal_lines!inner(...)` + `.eq("journal_lines.account_id", kasAccountId)` so Postgres filters to just Kas-account lines server-side instead of shipping every account's lines over the wire — and that query now runs in parallel with the period's entries query instead of before it.
- Dashboard home (`(dashboard)/page.tsx`): business/expenses/openShift parallelized (transactions query still has to wait, since its table name depends on `business.business_type`).
- Verified E2E on the Dev DB test account ([[test-account-preview]]): all 4 pages render correct, cross-consistent numbers (Kas & Bank Rp15.000 in Neraca matches Saldo Kas Akhir in Arus Kas across "Semua"/"Bulan Ini"/"Hari Ini" period filters — the "Hari Ini" case is the one that actually exercises the new filtered opening-balance query, since it's the only filter where prior-period activity exists to test against). `tsc`/`eslint` clean, no console errors.
- **Tooling gotcha hit again**: after editing these 5 files, all 5 routes 404'd until **two** full `preview_stop` + `rm -rf .next` + `preview_start` cycles — one wasn't enough. Matches the exact same Turbopack-on-slow-drive flakiness already documented above for new route folders; apparently editing files inside an existing `(dashboard)` route group can trigger it too, not just adding new folders.
- **Not yet done**: query result sizes still unbounded for large/old businesses (no `.limit()`, "Semua" period has no date bound at all, JS-side aggregation instead of SQL `SUM`) — acceptable for now since real businesses on this product are still small, but will matter once a business has months of transaction history. Revisit if "lemot" is reported again after data volume grows.

**Round 3, 2026-07-27 — the real "lemot" complaint, an actual paying client threatened to churn over it.** Root cause: the Android app is a thin Capacitor WebView pointing straight at the live site (`android-app/capacitor.config.ts` `server.url`), no local bundle — every navigation is a full server round trip, and `pos/page.tsx` used to `await` ~5 Supabase queries before Next could send any HTML. Fixed in stages (see [[kitchen-printer-lan-bluetooth]] for the printer half of that same session):
- POS screen made local-first: catalog data (products/open bills/customers/payment methods) moved off the blocking Server Component entirely into client-owned state, hydrated instantly from a new IndexedDB `pos_cache` store (`src/lib/pos-cache.ts`, `src/lib/offline-db.ts` bumped to v2), refreshed in the background via a new `getPosCatalog()` server action. Self-order polling switched from `router.refresh()` (re-fetches the whole page) to a dedicated lightweight action.
- `checkout()` (`pos/actions.ts`) used to run `logActivity` → kitchen-ticket-job-building → receipt-job-building sequentially (~8-9 DB round trips total) — parallelized with `Promise.all`.
- Result on the user's real device: app-open lag 14s → 7s, payment confirm 5s → 3s. First report of "no improvement" turned out to be the user not force-closing/reloading the app after deploy — always ask explicitly whether they did a full close+reopen (not just switched apps) before trusting a "still slow" report on this WebView-wrapped app.

**Known framework bug, don't retry**: `loading.tsx` (Next's file-based Suspense-fallback convention) breaks routing entirely on this project's Next.js build — every route 404s. Confirmed twice independently (once at the `(dashboard)` route-group root, once per-route in `settings/loading.tsx` alone); each time removing the file immediately restored normal routing, and it reproduced even after a full `.next` + `node_modules/.cache` wipe, so it is NOT the usual stale-Turbopack-cache flakiness documented above. **Don't add `loading.tsx` anywhere in this codebase.** Used `useLinkStatus` (from `next/link`, pure client-side, no new file under `app/`) instead — a pending spinner next to sidebar nav links in `dashboard-shell.tsx`, so tapping a link gives instant feedback instead of the previous page sitting frozen. This is cosmetic only (doesn't reduce real navigation latency) — backoffice pages other than POS still do their own blocking per-navigation fetch; would need the same local-first treatment as POS if raw speed on those pages becomes the complaint again.
