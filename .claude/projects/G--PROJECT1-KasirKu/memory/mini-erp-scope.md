**Tutup Buku (period closing) — built and verified E2E 2026-07-10**: new `public.period_closings` table (migration `20260710130000_period_closing.sql`, see [[supabase-migrations-manual]]) plus a `public.close_accounting_period(p_business_id, p_period_end)` RPC and a new `'tutup_buku'` value added to `journal_entries.source`'s check constraint. Mechanism: for every pendapatan/beban account with a nonzero all-time cumulative balance as of `p_period_end` (23:59:59+07 boundary, same convention as Neraca), the RPC posts one closing line that zeroes that account (debit a revenue account by its balance, credit an expense account by its balance), then one final line moving the net difference into `3-100 Laba Ditahan` (credit if profit, debit if loss) — built entirely from account balances computed server-side in plpgsql, passed to the existing `private.post_journal()` helper so it's guaranteed balanced. Key insight that kept this simple: because each closing zeroes the *all-time cumulative* balance (not a separate "since last close" window), no other report needed any code changes — Neraca's existing `totalPendapatan - totalBeban` query already naturally reflects only activity since the last closing, since prior activity nets to zero via the closing entry. RPC validates ownership, rejects future dates, and rejects closing at or before the last closing's `period_end` (enforces strictly increasing, no re-closing).
- New page `accounting/tutup-buku/page.tsx`: shows current unclosed Laba Berjalan (same calc as Neraca), last-closed date, a form to close as of a date (defaults to last day of previous month, confirm-step pattern like `MarkPaidButton`/`DeletePayslipButton`), and closing history. **5th bug found and fixed 2026-07-10** (user asked "sebagai accounting & finance saran apa yg kurang" — a fresh accounting-lens review after the mini-ERP feature set was otherwise complete): `checkout_transaction` credited the **full transaction total — including PPN collected from the customer — straight to 4-001 Pendapatan Penjualan**. Remitting the PPN later (paying the tax office) needs no new UI — the existing Jurnal Manual page already lists every account dynamically, so it's just a manual debit-2-200/credit-1-001 entry. Historical transactions posted before this fix keep their PPN baked into revenue (not retroactively corrected — would need a manual correcting entry if that matters).

**Real usability gap found and fixed 2026-07-18**: Melan hit this himself in his own real business data — posted a manual jurnal, realized it was wrong, and discovered posted entries can't be edited (correct by design, RLS is SELECT-only on `journal_entries`) but there was no actual feature to fix it, just written instructions telling users to "post a reversing entry" with nothing behind that. Also flagged that picking Debit vs Kredit is genuinely confusing for non-accountants with zero guidance in the UI. Both fixed same day (migration `20260718100000_journal_reversal.sql`, applied to both Dev and Production):
- **`reverse_journal_entry(business_id, entry_id, note)` RPC** — mirrors the existing `void_transaction` reversal pattern: posts a new entry with every line's debit/credit swapped from the original, dated *today* (not backdated, so it doesn't silently alter a closed period), tagged `source='koreksi'`. Only works on `source='manual'` entries, and blocks reversing the same entry twice (checks for an existing `koreksi` entry with `source_id` = the original). New `"↩ Koreksi"` button per manual entry on the Jurnal page (hidden once already reversed, hidden on non-manual entries) opens an inline confirm with an optional reason note.
- **Plain-language Debit/Kredit hints** — `accounts.type`/`normal_balance` already existed in the schema but the Jurnal page's query never selected them. Now it does, and `add-journal-form.tsx` shows a dynamic hint under each line based on the selected account's type (e.g. "Kas/aset bertambah → isi Debit. Berkurang → isi Kredit." for aset, "Modal bertambah → isi Kredit. Ditarik/berkurang → isi Debit." for modal) — no accounting jargon, just what actually happens in plain Indonesian.
