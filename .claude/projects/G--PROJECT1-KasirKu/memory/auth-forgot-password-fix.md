Two bugs, found and fixed in sequence the same day — the first fix was real but incomplete; keep both rounds in the record since the second round's root cause supersedes the first's explanation.

**Round 1**: user reported clicking the password-reset email link landed on `/login` instead of the "buat password baru" form. Cause: `forgot-password/page.tsx`'s `redirectTo` pointed at `/auth/callback?next=/reset-password`, which only knows how to exchange a `?code=` query param. Fixed (`dee0010`) by pointing `redirectTo` straight at `/reset-password`. This was **correct as far as it went**, but exposed a second, deeper bug immediately.

**Round 2**: user reported `Auth session missing` within under a minute of opening the (now correctly-routed) reset-password form and typing a new password. **Actual root cause, confirmed by reading the installed package source** (`node_modules/@supabase/ssr/dist/main/createBrowserClient.js`): the shared browser client (`src/lib/supabase/client.ts`, used everywhere else in the app) is built via `@supabase/ssr`'s `createBrowserClient`, which **hardcodes `flowType: "pkce"` — spread in after the caller's own options, so it cannot be overridden via any config passed in**. PKCE requires a `code_verifier` generated at request time (when `resetPasswordForEmail` was called) to still be present in that *same* browser when the email link is later opened. Password recovery links get opened anywhere — a different browser, a phone, an in-app email client webview — so the verifier is essentially never there, and the exchange silently produces no session, even though the page itself loads fine and looks normal. This is a well-known structural weak point of PKCE for password-recovery specifically (as opposed to login/signup, where same-browser continuity is much more likely).

**Fix** (`5c002eb`): new `src/lib/supabase/recovery-client.ts` exports `createRecoveryClient()` — a **separate, plain `@supabase/supabase-js` client** (not the `@supabase/ssr` wrapper), explicitly forced to `flowType: "implicit"` and `persistSession: false`. Both `forgot-password/page.tsx` (calling `resetPasswordForEmail`) and `reset-password/page.tsx` (calling `updateUser`) now use this client instead of the shared one — Supabase generates the email's `{{ .ConfirmationURL }}` based on the flow type of the client that requested it, so this alone makes the link carry `#access_token=...&type=recovery` (no `code_verifier` dependency, works from any device/browser). No Supabase dashboard/email-template change was needed — `{{ .ConfirmationURL }}` adapts automatically per-request.

**Also hardened while fixing this**: `reset-password/page.tsx` previously created a throwaway client instance inside `handleSubmit` (would have lost any in-memory-only session immediately with `persistSession: false`) — now creates **one** recovery-client instance via `useState(() => createRecoveryClient())` for the whole page lifetime, and added an explicit mount-time check (`getSession()` + `onAuthStateChange` listening for `PASSWORD_RECOVERY`) that shows a clear "Link Tidak Valid atau Kedaluwarsa" state with a "Minta Link Baru" button **before** the user ever gets to fill out a form that was always going to fail — instead of only surfacing the raw `Auth session missing` string at submit time. Also changed the post-success screen's CTA from `router.push("/dashboard")` to a link to `/login`, since this recovery client's session is intentionally separate from the app's real cookie-based session (the password change itself is real and account-wide regardless of which client made the call — only the "stay logged in afterward" convenience was removed, which is an acceptable and arguably more correct trade-off).

Verified in browser (dev DB, see [[supabase-dev-prod-split]]): `/reset-password` with no token now correctly shows the "Link Tidak Valid" state instead of a doomed-to-fail form; `forgot-password` submission still succeeds and shows "Cek email kamu" using the new recovery client; no console errors; `tsc`/`eslint` clean. **Could not verify the full real-email-click path end-to-end** (no inbox access in this environment) — if a variant of this bug ever resurfaces, that's the step to check manually, and re-verify against the actual `{{ .ConfirmationURL }}` the email contains (should now contain `#access_token=`, not `?code=`).

**Tooling note**: the submit-button's first `computer`-tool click silently no-op'd (no network request) on both the forgot-password and reset-password forms — same hydration-race flakiness already documented in [[test-account-preview]]. `javascript_tool` `.click()` worked immediately both times.

**How to apply**: any *other* future feature on this project that needs a Supabase auth flow which must survive being opened in a different browser/device than the one that initiated it (password recovery is the main one, but e.g. an "invite teammate" email link would have the same problem) should use `createRecoveryClient()` (or a similarly implicit-flow client), not the shared `@supabase/ssr` client — the PKCE hardcoding in `createBrowserClient` is a library-level constraint, not something fixable by passing different options.
