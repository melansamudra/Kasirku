**What the reference is**: a fully self-contained client-side-only prototype (vanilla JS, localStorage, no backend/auth/multi-tenant) covering Dashboard, Jurnal, Laba Rugi, Neraca, Arus Kas, Target vs Aktual, Daftar Akun, Rekonsiliasi Rekening (per payment-method + merchant fee), Invoice/Nota, Notifikasi center, Kas Harian (simplified cashier log), Supplier & Hutang, Absensi, Payroll (with configurable tunjangan/BPJS/lembur multiplier settings), Rekap Absensi Bulanan, Lembur (hours × rate × 1.5x/2x law multiplier), THR (auto tenure-based per PP 36/2021), Data Karyawan, Pengaturan. Visual style: dense enterprise SaaS look, orange accent (#e8611a), 13px base font, pill badges, toggle switches — different from KasirKu's current brand-green Tailwind look.

**Gap analysis vs KasirKu's actual accounting/HR code (verified 2026-07-14, see [[mini-erp-scope]] for what was already built)**:
- **Already covered, often more mature — no rebuild needed**: Jurnal, Laba Rugi (cash + akrual, 2 versions), Neraca, Arus Kas, Target vs Aktual (Anggaran), Daftar Akun, Supplier & Hutang, Payroll basics, Absensi harian. **Rekonsiliasi Rekening in `finance/page.tsx` is already richer than the reference** (per-payment-method POS-vs-bank + configurable merchant fee %, backed by a real `merchant_fees` table) — reskin only, no functional work.
- **Rekap Absensi Bulanan**: exists but embedded inside `attendance/page.tsx`, not a standalone page like the reference has.
- **Genuine gaps (new features, zero existing code)**: Invoice/Nota (client name, line items, DP, due date, print — nothing like this exists, POS receipts are pay-in-full only); Notifikasi/Reminder center (also blocked on a missing `contract_end` field on employees — doesn't exist at all today); bulk "export everything" to Excel (only per-page CSV exists today); a global period switcher synced across all report pages (every report page currently filters its own period independently, and `finance/page.tsx` even uses an incompatible `Period` type from the shared `reports/period.ts` helper).
- **Kas Harian** (simplified non-accounting cash in/out log for cashiers): missing as a dedicated page, but likely a thin UI layer over the existing expense/journal auto-posting pattern (`finance/actions.ts` `addExpense`) rather than new backend — feasible without new schema.
- **Design-philosophy conflicts, not simple gaps — need an explicit decision, not just "build it"**:
  - Lembur: KasirKu's payslip has `lembur_amount` as manual-nominal-only (deliberate 2026-07-10 decision, "varies too much per business to hardcode" — see [[mini-erp-scope]]). Reference computes hours × hourly-rate × 1.5x/2x law multiplier automatically.
  - THR: same pattern — KasirKu's `thr_amount` is manual-nominal; reference auto-calculates from tenure per PP 36/2021 (≥12mo → 1 full month salary, proportional under 12mo).
  - Payroll komponen gaji settings (toggleable tunjangan jabatan/makan/transport, configurable BPJS Kesehatan/Ketenagakerjaan %, kasbon tracking) is a materially bigger feature than KasirKu's current free-form "tunjangan/potongan" per-payslip line-item model — not yet scoped as small or large.

**Architecture decision — made 2026-07-14 via AskUserQuestion**: user chose **"Modul dari KasirKu"** over a from-scratch standalone/offline app. This means: reuse the existing Supabase multi-tenant double-entry accounting engine (journal, RLS, tutup buku, etc. — already built and E2E-verified per [[mini-erp-scope]]) rather than throwing it away for a localStorage clone like the reference itself or like [[kalkulator-hpp-desktop]]'s zero-server approach. The product will be a repackaged/re-skinned subset or superset of KasirKu's existing accounting+HR module, sold/priced separately, still requiring a server/subscription (not a one-time zero-ongoing-cost sale like the HPP desktop app).

**Remaining 3 scoping questions — answered 2026-07-14**:
1. **Lembur & THR**: stay **manual-nominal, flexible** — user explicitly rejected the reference's automatic UU-formula calculation ("flexible saja"). No change needed to existing payslip behavior; not a gap to close.
2. **Payroll komponen gaji settings** (BPJS %, toggleable tunjangan jabatan/makan/transport, kasbon tracking): **deferred, not in scope for now** ("ini nanti dulu"). Do not build this yet.
3. **Product packaging**: stays on the **same KasirKu website/domain**, but as its **own distinct section**, same pattern as [[kalkulator-hpp-desktop]] (which has its own marketing page `/kalkulator-hpp` + its own purchase flow `/kalkulator-hpp/beli`, separate from the main app nav). Since the architecture decision above was "reuse the existing Supabase accounting engine" (not a standalone offline app like the HPP desktop), this likely means: a dedicated landing/marketing page + its own pricing/plan for the finance module, still requiring login/subscription (unlike the HPP desktop's one-time zero-server sale) — exact mechanics (new plan tier in `src/lib/billing/plans.ts`? new business type? feature-gated view within the existing dashboard?) still need to be worked out at implementation time, not yet decided.

**Net effect of these 3 answers**: the actual build scope is now smaller than the original gap list — cut Lembur auto-calc, THR auto-calc, and payroll komponen settings entirely. Remaining real gaps to close if/when this gets built: Invoice/Nota, Notifikasi/Reminder center (+ new `contract_end` employee field), Kas Harian simplified log, standalone Rekap Absensi Bulanan page, global period switcher, bulk Excel export, plus the new marketing/pricing page and a visual redesign (adapt the reference's dense layout but recolor to KasirKu's actual brand green, matching the precedent set in [[kalkulator-hpp-desktop]]'s UI redesign, not the reference's literal orange accent).

Explicit target customer: businesses that **already have their own POS/cashier system** and only want the accounting/finance/HR module — they should be able to buy just that, without paying for or seeing Kasir/Produk/Meja features. Concretely this means: a new `PlanCode` in `src/lib/billing/plans.ts` (e.g. `"finance_monthly"`/`"finance_yearly"`) alongside the existing `monthly`/`yearly`/`lifetime`, plus gating logic (likely in `dashboard-shell.tsx`'s `buildNavGroups` and/or route-level checks) that hides POS-related nav groups (Kasir, Operasional's product/table/stock items) for accounts on a finance-only plan, showing only Akuntansi/SDM/relevant Kas & Rekening pages. Implementation decisions made beyond the plan's literal schema (all reasoned, not spec deviations to worry about):
- Added a `customer_name text not null` column to `invoices` alongside the optional `customer_id` FK — the plan's schema only listed `customer_id`, but "nama klien" was a stated requirement and forcing a pre-existing customer record for every ad-hoc invoice client would be more friction than the feature needs. Selecting an existing customer in the form auto-fills the name (still editable).
- Added a stored `subtotal numeric` column on `invoices` (computed once at creation from line items) rather than joining `invoice_lines` on every list-page render — denormalized but simpler, same pattern as `purchases.amount`.
- Status is **computed automatically** from `dp_amount` vs `subtotal` at creation (`unpaid`/`partial`/`paid`) — no UI path to the `draft` status the check-constraint still allows for future use; the only manual transition built is "Tandai Lunas" (forces `paid`), per the plan's minimal verification bar. No "edit invoice line items after creation" flow was built — only create + mark-paid, since nothing in the plan's verification steps required editing, and a dynamic line-item editor on an existing invoice would have meaningfully expanded scope.
- Invoice numbering: `INV-YYYYMMDD-<6-digit-ms-suffix>` computed in the server action (not a DB sequence/RPC) — same simple timestamp-based approach as `billing/actions.ts`'s order IDs, per the plan's explicit "keep it simple" allowance.
- Server action `createInvoice`/`markInvoicePaid` are called **directly with plain object args from the client** (not via `<form action>`/FormData) — matches the existing precedent in `pay-button.tsx`/`buy-form.tsx` for actions needing structured (non-form-serializable) data like the line-items array.
- `invoice_lines` RLS uses an `exists`-subquery against `invoices.business_id` (same pattern as `journal_lines`→`journal_entries`), but unlike `journal_lines` (select-only, since journal balance is a protected invariant enforced only via RPC), `invoice_lines` grants direct client `for all` since there's no analogous invariant to protect for a plain document table.

**Mechanism**: new `PERIOD_COOKIE_NAME` constant in `reports/period.ts` (plain string, safe to import from both server pages and the new client component) + a new shared `reports/period-tabs.tsx` **client component** (`"use client"`) that renders the same pill-tab UI every page used to duplicate inline, and on click does `document.cookie = "kk_period=<value>; path=/; max-age=1y"` before letting the `<Link>` navigate normally (no `preventDefault`, so soft-navigation still works). Each of the 10 server pages now resolves its period as `parsePeriod(periodParam ?? (await cookies()).get(PERIOD_COOKIE_NAME)?.value)` instead of just `parsePeriod(periodParam)`. Deliberately **not** done via `proxy.ts`/middleware — reading the cookie is a normal `next/headers` `cookies()` call inside each Server Component, which the plan's own "server-component + searchParams" preference pointed at directly; a middleware redirect layer would have been a heavier, less transparent way to get the same result.

**Scope decision**: only the period **type** (today/week/month/all/custom) is remembered — custom's specific `from`/`to` dates are not persisted (they're page-specific typed input, impractical to globally sync the same way). One consequence observed during verification: clicking "📅 Kustom" itself (even before filling dates) remembers `period=custom` in the cookie; visiting another page next with no dates set then falls back to `getPeriodRange`'s empty-custom-range behavior, which is equivalent to "all" (both bounds null) — not a bug, just the natural consequence of not syncing the dates themselves. Not worth engineering around.
