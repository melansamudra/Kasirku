  - **Bug hit and fixed during verification**: the eligibility filter used `purchase_date <= period` (period = first-of-month) which wrongly excluded assets bought mid-month (e.g. bought the 10th, period="...-01" → excluded). Fixed to compare against the *last* day of the period's month instead.

  - **Data cleanup consequence, real and worth remembering**: the first bug fix required a page reload + retry, but the *second* (RLS) failure happened **after** the journal-posting RPC call had already succeeded (post_journal_entry is security-definer, unaffected by the depreciation_postings RLS gap) — so the failed attempt still posted a real "Beban Penyusutan 2026-07" journal entry before erroring out on the tracking-table insert. The next successful retry posted a *second* identical entry, leaving Akumulasi Penyusutan double-counted (Rp200.000 instead of Rp100.000) even though `fixed_assets.accumulated_depreciation` and `depreciation_postings` only reflected one. Caught by comparing the Aset Tetap page's book value against Neraca's Akumulasi Penyusutan line — they should always match and didn't. Fixed via a manual reversing journal entry (debit 1-501/credit 5-105, Rp100.000) through the Jurnal Manual page, per the app's established "correct via reversing entry, don't edit old rows" convention — not by deleting the duplicate journal_entries row. **Lesson for any future multi-step server action that calls a security-definer RPC before a plain-RLS insert**: if the plain insert can fail independently, the RPC's effect is not transactional with it and can leave an orphaned side-effect: sanity-check derived totals (e.g. a book-value calc) against the source-of-truth ledger (Neraca) after any action that touches both, not just after known-risky ones.

- **Laporan Perubahan Modal + Setoran/Prive** — new page `accounting/modal/page.tsx` ("📜 Perubahan Modal" in Akuntansi) with quick one-click "+ Setoran Modal"/"− Ambil Prive" forms (2-line manual journal against 1-001/3-001) plus a Statement-of-Changes-in-Equity report. Key design choice that avoids re-deriving pendapatan/beban per period (which would double-count if a Tutup Buku landed mid-period, see the Tutup Buku section above): compute Total Modal (`Modal Pemilik + Laba Ditahan + Laba Berjalan`, same 3-part sum Neraca uses) as of two snapshots — strictly before the period start, and as of the period end — then `Laba Bersih Periode Ini = (ModalAkhir − ModalAwal) − (Setoran − Prive)`, where Setoran/Prive come from summing credit/debit lines on the 3-001 account specifically within the period. This is mathematically exact regardless of whether a closing happened mid-period, without needing any closing-aware special-casing. Verified: Modal Akhir (period=all) matched Neraca's Total Modal exactly both before and after posting a real Rp1.000.000 setoran (which correctly flowed through to both pages identically and left "Rugi Bersih Periode Ini" unchanged, proving setoran/prive are cleanly separated from the profit figure).

**Tutup Buku (period closing) — built and verified E2E 2026-07-10**: new `public.period_closings` table (migration `20260710130000_period_closing.sql`, see [[supabase-migrations-manual]]) plus a `public.close_accounting_period(p_business_id, p_period_end)` RPC and a new `'tutup_buku'` value added to `journal_entries.source`'s check constraint. Mechanism: for every pendapatan/beban account with a nonzero all-time cumulative balance as of `p_period_end` (23:59:59+07 boundary, same convention as Neraca), the RPC posts one closing line that zeroes that account (debit a revenue account by its balance, credit an expense account by its balance), then one final line moving the net difference into `3-100 Laba Ditahan` (credit if profit, debit if loss) — built entirely from account balances computed server-side in plpgsql, passed to the existing `private.post_journal()` helper so it's guaranteed balanced. Key insight that kept this simple: because each closing zeroes the *all-time cumulative* balance (not a separate "since last close" window), no other report needed any code changes — Neraca's existing `totalPendapatan - totalBeban` query already naturally reflects only activity since the last closing, since prior activity nets to zero via the closing entry. RPC validates ownership, rejects future dates, and rejects closing at or before the last closing's `period_end` (enforces strictly increasing, no re-closing).
- New page `accounting/tutup-buku/page.tsx`: shows current unclosed Laba Berjalan (same calc as Neraca), last-closed date, a form to close as of a date (defaults to last day of previous month, confirm-step pattern like `MarkPaidButton`/`DeletePayslipButton`), and closing history. Not enforced across every posting action (purchases/finance/payroll/POS checkout) since that's a much bigger change; documented in the confirm-dialog copy as a "don't do this" convention instead, matching the existing "correct via reversing entry, not by editing old data" philosophy already used on the Jurnal page.

**Formula audit — 2026-07-09**, after all the above was built, ran 4 parallel Explore agents auditing every calculation in the app (POS checkout/merchant-fee, HPP/COGS/weighted-avg cost, accounting/journal/balance-sheet, payroll/shift-close/ticket-pricing). Most formulas checked out clean (checkout math, weighted-average cost, Neraca arithmetic, Anggaran variance, payroll, shift-close, ticket pricing — the last one has existing passing unit tests, 38/38). **4 real bugs found, 1 fixed so far:**
1. **FIXED (commit bdbe337)**: Arus Kas (`accounting/arus-kas/page.tsx`) bucketed cash flow by `journal_entries.source`, but `public.post_journal_entry` (used by every purchase and expense posting, not just true manual entries) always writes `source='manual'` — so nearly all purchases/expenses were misclassified into "Investasi & Pendanaan" instead of "Operasional". Fixed by classifying by the counterparty account's type/code instead (modal→Pendanaan, Peralatan 1-500→Investasi, else→Operasional). Verified in browser: Beban Lain-lain, Bayar Utang Dagang, and a cash Persediaan purchase all correctly moved to "Aktivitas Operasional".
2. **FIXED (commit b928d51)**: `recalculateProductCost()` (`products/[productId]/recipe/actions.ts`) only used to re-fire on recipe line add/remove — never when an ingredient's `unit_cost` changed via `ingredients/actions.ts` `editIngredient`, `finance/actions.ts` `addExpense`, or `purchases/actions.ts` `addPurchase`, so `products.cost` (and downstream, `transaction_items.cost` snapshotted at sale time → COGS Teori) silently went stale. Fixed by extracting the calc into `src/lib/recalculate-product-cost.ts` (`recalculateProductCost` + a new `recalculateProductCostsForIngredient` that finds every product referencing a given ingredient and recalcs each) and calling the ingredient-scoped version from all three write sites whenever `unit_cost` actually changes. Verified in browser on "Toko Test Laporan": added Gula Pasir (50gr) to Roti Bakar's recipe (HPP → Rp1.350 at Rp27/gr), then edited Gula Pasir's price to Rp100/gr manually — Roti Bakar's HPP updated to Rp5.000 without touching the recipe. Then bought 100gr more via the Pembelian page (weighted avg → Rp106/gr) — HPP updated again to Rp5.300, confirming all three trigger paths work.
3. **FIXED (commit e02e62d, migration `20260709120000_fix_zero_total_hpp_posting.sql`)**: `checkout_transaction` only posted a journal entry `if v_total > 0`, but stock/ingredient consumption happens unconditionally — a 100%-discounted sale reduced inventory with no HPP/Persediaan journal line at all. Fixed by decoupling the Kas & Bank/Pendapatan lines (posted only when `v_total > 0`) from the HPP/Persediaan lines (posted independently whenever `v_total_cost > 0`), building `v_journal_lines` incrementally and only calling `private.post_journal` if at least 2 lines ended up in it. Mirrored the identical fix in `void_transaction`'s reversing entry. Verified end-to-end in browser on "Toko Test Laporan": sold 1 Roti Bakar (HPP Rp5.300) with a 100% order discount (INV-20260709-0001, total Rp0) — jurnal correctly posted a 2-line entry (debit 5-001 HPP / credit 1-200 Persediaan, Rp5.300, no Kas & Bank/Pendapatan lines). Then voided it with manager PIN — reversing entry correctly posted debit 1-200 / credit 5-001, Rp5.300. Neraca stayed balanced throughout.
4. **FIXED (commit 23c83ca)**: `purchases/actions.ts` and `finance/actions.ts` called the `post_journal_entry` RPC via `supabase.rpc(...)` without checking `{ error }`. Now `postExpenseJournal`/`postPurchaseJournal` return the error message (or null) instead of swallowing it, and both call sites plus the utang-payment RPC call in `addPurchasePayment` check it: on failure they log a `"warning"` activity entry (instead of the usual success level) with the error text, and return a form error telling the user the record saved but a manual correcting journal entry is needed at Akuntansi → Jurnal. Verified no regression on the happy path (a normal "Lain-lain" expense still saved silently with no error banner). The failure path itself wasn't exercised (would need deliberately breaking an account code) but the logic is a straightforward null-check/ternary, low risk.

**5th bug found and fixed 2026-07-10** (user asked "sebagai accounting & finance saran apa yg kurang" — a fresh accounting-lens review after the mini-ERP feature set was otherwise complete): `checkout_transaction` credited the **full transaction total — including PPN collected from the customer — straight to 4-001 Pendapatan Penjualan**. PPN isn't the business's revenue, it's a liability held on behalf of the tax office, so every taxed sale was overstating income with no corresponding "PPN payable" anywhere in Kewajiban. **Fixed migration `20260710140000_ppn_liability.sql`**: added `2-200 PPN Keluaran (Utang Pajak)` to the seeded COA (via `seed_default_accounts` + backfill for existing businesses), and redefined `checkout_transaction` to credit only `subtotal + service` to Pendapatan Penjualan while crediting `tax` to the new liability account instead (Kas & Bank debit for the full total is unchanged). `void_transaction`'s reversing entry mirrors the same split. Remitting the PPN later (paying the tax office) needs no new UI — the existing Jurnal Manual page already lists every account dynamically, so it's just a manual debit-2-200/credit-1-001 entry. Historical transactions posted before this fix keep their PPN baked into revenue (not retroactively corrected — would need a manual correcting entry if that matters).

Built 2026-07-12, closing the #1 launch blocker identified in a full codebase audit (see [[project-purpose-saas-product]]): before this, there was no way for anyone to pay for KasirKu at all. User's decisions that shaped the design: both a recurring subscription AND a one-time lifetime purchase (not subscription-only), **Midtrans** as the gateway, **no trial** (must pick+pay immediately after signup), and a **3-day grace period** (past_due banner) before a lapsed subscription actually locks the account out.

**Schema** (migrations `20260712110000_billing.sql` + `20260712120000_admin_billing_columns.sql`): `public.subscriptions` (one row per business, mutated in place — `status` unpaid/active/past_due/expired, `plan_code`, `period_end` null=lifetime) and `public.payments` (append-only Midtrans transaction log). RLS is deliberately narrow: a business can SELECT its own rows and INSERT exactly one `unpaid` subscription (at onboarding) / any number of `pending` payments (to start a Midtrans transaction) — but can never write `active`/`settlement`/etc itself. Only the service-role Midtrans webhook and cron sweep can transition status, so a tenant can never mark itself paid. Plan catalog (name/price/period) is a **TS constant** (`src/lib/billing/plans.ts`), not DB-driven — fast to ship, revisit if pricing needs to change without a deploy. **Prices are placeholders** (Rp99rb/bulan, Rp990rb/tahun, Rp2,5jt lifetime) — must be edited before real launch, no real pricing input was given.

**Existing businesses were grandfathered** — the billing migration backfills every pre-existing business with a permanent `active`/`lifetime`/`period_end=null` subscription row, so toko-toko test yang sudah ada tidak mendadak terkunci begitu migrasi jalan. This was almost missed — caught before applying the migration, not after.

**Enforcement**: two independent Server Component layouts do the actual lockout — `(dashboard)/layout.tsx` and a new `pos/layout.tsx` — both call `getSubscriptionAccess()` (`src/lib/billing/status.ts`) and `redirect()` to `/business/<id>/billing` if locked (`unpaid`/`expired`). Deliberately NOT one shared `[businessId]/layout.tsx` wrapping everything, since that would redirect-loop on the billing page itself (Next.js layouts can't easily detect "am I currently the billing page"). `(dashboard)/layout.tsx` also shows a past_due warning banner (amber, in `dashboard-shell.tsx`) with a link to `/billing` — pos doesn't need the banner, cashiers don't need to see billing state.

**Payment flow**: `billing/actions.ts` `createPayment()` inserts a `pending` payment row, then calls Midtrans Snap's create-transaction API (sandbox vs production host picked via `MIDTRANS_IS_PRODUCTION`), returns a `redirect_url` the client does a plain `window.location.href` to (no Snap.js popup SDK). Webhook at `src/app/api/midtrans/notification/route.ts` verifies the `sha512(order_id+status_code+gross_amount+MIDTRANS_SERVER_KEY)` signature, uses a **new service-role Supabase client** (`src/lib/supabase/service.ts` — first use of `SUPABASE_SERVICE_ROLE_KEY` in this codebase, only ever import this in the webhook/cron, never in user-facing code), flips `payments.status` and (idempotently — checks for already-`settlement` first) activates the subscription, extending `period_end` from the greater of now-or-existing-period_end (so early renewal doesn't lose paid days). Daily cron (`vercel.json` + `src/app/api/cron/subscription-sweep/route.ts`, guarded by `CRON_SECRET` bearer header) ages `active`→`past_due` (period_end passed) →`expired` (past_due + 3 days).

**Bug found and fixed during E2E testing**: `src/lib/supabase/middleware.ts`'s public-path allowlist didn't exempt `/api/*` routes, so Midtrans's webhook and Vercel's cron caller — both server-to-server with zero browser session — were being redirected to `/login` instead of reaching the route handler at all. Fixed by adding `/api/midtrans` and `/api/cron` to `isPublicPath`. Caught by literally curling the webhook locally and getting back the string `/login` instead of JSON — a good reminder to always hit new API routes with a bare curl (no cookies) as part of verifying them, not just through the browser (which carries a session and would have masked this).
